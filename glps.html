§00 — Case file T-01

Client work · Computer-aided dispatch

Dispatch for Great Lakes Patient Services

A computer-aided dispatch (CAD) and patient-care records system for a non-emergency medical transport operator in Ontario. It started as a single-file prototype holding everything in memory. We are turning it into a multi-user application with a real database, sign-in, and access control strong enough for patient health information.

§01 — The brief

What GLPS needed

From prototype to a system of record

GLPS runs non-emergency patient transfers: stretcher, wheelchair, and ambulatory. Their dispatch tool worked as a demo. Units, calls, schedules, and patient care reports all lived in one HTML file and vanished on reload.

The brief had three conditions:

  • No regressions. Every feature of the prototype survives, now backed by a database.
  • Access enforced at the database, not just by hiding screens, so nobody can bypass it through the API.
  • Built to hold patient health information. Encryption, audit logging, and role-based access come before any real patient data goes in.

The work runs as a seven-step plan, one step at a time. Each step is verified before the next one starts.

§02 — The CAD model

How a transport moves through the system

Book, dispatch, roll, record

Every transport follows one path. The steps that move it forward run as single database transactions, so the board, the crew tablet, and the clinical record can't disagree.

01 · Book

The schedule board

  • A day planner with one lane per unit, in timeline and list views.
  • Pickups are booked as a window, not a single deadline.
  • A round trip creates a real return-leg booking, with its own crew, run sheet, and number, so the trip home is never forgotten.
  • Held slots can reserve a specific unit, so two dispatchers can't promise the same crew the same hour.
  • Board colors are computed in the database, so the list, timeline, and legend always agree.
02 · Dispatch

One transaction, no half-states

  • Promoting a booking creates the call, sets the unit en route, links the booking, and opens the run sheet, all in one transaction. A half-finished dispatch can't exist.
  • Reassigning a live call moves the crew in the same step, so the board and the tablet never disagree about who is driving.
  • An address registry builds itself from calls. It deduplicates addresses, keeps entry codes and instructions, and raises an alert on the dispatch screen when an active call touches a flagged address.
03 · On the road

Unit status from the crew tablet

  • Crew set their own unit's status; dispatch can override it. Crew can't change another unit's status.
  • Statuses that mark a moment in the transport (arrived, transporting, destination) stamp the run sheet automatically.
  • The first press wins. A stray tap can't rewrite a time on a clinical record; corrections go through the amendment process.
  • Tablets update live by subscription, so the crew sees a dispatch the moment it happens.
04 · Record

Run sheet and patient care report

  • The run sheet is the dispatch record (mobility, escorts, precautions, disposition, transfer signatures). It opens automatically at dispatch.
  • The patient care report is the clinical assessment, modeled on the operator's paper form. It's created only when there is something to assess. No field is captured in both records, so they can't contradict each other.
  • Record numbers encode the record type, the date, and the author's initials.
  • A submitted record is locked. Only its author can amend it, and only with a written reason. Dispatch can void, reopen, or correct a call the same way. Every change lands in a change audit log.
§03 — Safeguards

Patient health information

Access control that holds at the database

Hiding a tab is presentation, not security. Each control below is enforced where the data lives, and most are checked by automated tests.

ControlHow it's enforced
Role-based accessFive roles: admin, management, dispatch, crew, billing. Each role's screens are configurable in the app, and the same rules are enforced by row-level security in the database. A test suite signs in as each role and checks what it can reach.
Crew scopingCrew see only their own unit's calls and bookings. Signing off shift removes that access immediately.
Audited patient readsPatient records can't be read with a plain query. Every read goes through a server function that writes an audit entry first. The audit log is append-only.
Locked recordsSubmitted run sheets and reports are locked by the database itself. Amendments need the original author and a reason, and every change is recorded.
Device securityThe live session is held in memory only. What the tablet stores is encrypted with a key derived from the crew member's PIN, so a lost tablet holds nothing usable.
Data residencySelf-hosted in Canada. Ontario's health-privacy law (PHIPA) requires a written agreement whenever patient data goes to an outside service provider. Self-hosting removes that provider, and the job becomes securing the server properly.
No card dataPayment details never touch the database; a payment processor handles them. The build fails if a card-like column ever appears.
OperationsScheduled backups of both the records and the signature images, checked by a scripted test restore. Failed sign-ins are monitored.
